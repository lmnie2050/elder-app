# 銀髮族 App — AI 助理專案交接脈絡

> 整理日期：2026/09/30（第二版，加入 repo 與協作流程）
> 用途：新成員加入或開新對話時，貼進去快速掌握全貌

---

## 一、這是什麼

一款主打運動與飲食的銀髮族 App，首頁有一個 AI 助理角色。

**互動方式**：使用者點選人物 → 跳出小框 → 顯示今天的運動與飲食狀況 → 使用者可以輸入訊息並得到回應。

**不是聊天機器人**。單次問答，沒有多輪對話記憶。定位接近「助理」而非「對話夥伴」。

這個定位是刻意的，也簡化了實作：原本規劃的跨輪次規則（每五輪一次示弱句型、同一建議七天內最多提兩次）大部分不需要實作。

副作用是評測可信度提高——每次請求都是獨立的，Promptfoo 測的就是線上真實行為，不會因為上下文不同而失準。

### 子功能關係

```
成品 App
├── 首頁 AI 助理      ← 本文件的範圍
├── 飲食記錄子功能    ← 另有專案，Unity + 另一支 Worker
└── 二選一問答子功能
```

助理會讀運動與飲食紀錄，答題結果優先度低。

## 二、角色定位與個性

**角色**：阿明，社區關懷據點的訪視員，五十八歲，不太會煮菜。

**定位是「認識你、記得你的事、關心你但不管你」。**

明確排除的兩種角色：
- **孫子／孫女**：會引發過度期待，漏接時失落感大
- **護理師／健康管家**：會被當成醫囑，踩法遵紅線

### 四個特質（每項都有取捨）

| 特質 | 說明 | 犧牲了什麼 |
|---|---|---|
| 慢 | 先問狀況再給建議 | 效率，換取被聽見的感受 |
| 不勸 | 說完就放手，不追蹤 | 行為改變的數字，換取留存 |
| 會示弱 | 偶爾請對方教自己 | 權威感，換取被需要的感覺 |
| 有小設定 | 不太會煮菜 | 無，讓角色成為一個「誰」 |

## 四、系統架構

一次請求的完整流程：

```
使用者輸入
   ↓
[1] 前置安全分類器      ← 純程式，命中就直接回固定文字
   ↓ （未命中）
[2] 每日摘要             ← 程式算好的數字，模型不自己數   ※未實作
   ↓
[3] 主題選擇             ← 程式決定聊什麼                  ※未實作
   ↓
[4] 降級判斷 + 服藥閘門  ← 依個人檔案完整度                ※未實作
   ↓
[5] 主模型               ← 只負責把主題寫成一兩句人話
   ↓
[6] 後置檢查             ← 攔截違規內容
   ↓
[7] 回傳
```

**關鍵原則：第 1、2、3、4、6 步全是程式，模型只出現在第 5 步。**

這樣規則才是真的規則，不是拜託模型遵守。

### 為什麼數字一定要程式算

實測證據：飲食 App 的週回顧原本讓模型評分，同一份清單刪掉一筆菜，油炸分數就從 4 掉到 2，蔬菜分數從 2 掉到 1。語言模型算頻率本來就不穩定。

助理報告步數時如果講錯數字，比評分錯更傷信任。

### 三層降級（尚未實作）

| 層級 | 條件 | 行為 |
|---|---|---|
| L0 | 無個人資料 | 只做陪伴，不給任何具體數字 |
| L1 | 有基本資料 | 通用提醒 |
| L2 | 含習慣與限制 | 才給具體建議 |

L2 的營養建議必須先過「是否服藥中」閘門。

## 五、安全機制

### 前置分類器（`safety.ts`）

純關鍵字比對，零延遲零成本，在任何 AI 呼叫之前執行。命中就直接回傳寫死的文字，完全不碰模型。

| 類別 | 涵蓋 | 回應 |
|---|---|---|
| `medical` | 胸痛、喘不過氣、跌倒、單側無力、口齒不清、大量出血、意識不清 | 引導 119 或聯絡家人 |
| `emotional` | 活著沒意思、拖累家人、交代後事、不想醒來 | 提供 1925 安心專線、1995 生命線 |

**設計原則：寧可誤報。** 把正常對話誤判成緊急狀況，代價是阿明大驚小怪；漏掉真的緊急狀況，代價是人命。

**回應文字寫死。** 緊急狀況不讓模型即興發揮。這也代表 Workers AI 當機時，緊急引導照樣會出現。

> 台灣 65 歲以上是自殺率最高的年齡層之一，情緒風險那組不能漏。專線號碼與服務時間上線前要再確認一次。

### 後置檢查

攔截模型說出口的違規內容：藥物相關、數值判讀、做不到的承諾。命中就換成安全的替代句，並把原始回應寫進 log 當作改 prompt 的素材。

### 已知限制

關鍵字法擋不到委婉講法。長輩常說「我這裡怪怪的」「最近都不太想動」，字面上沒有紅線詞。

原規劃的第二層是小模型二次確認，處理這類情況。**尚未實作。**

台語與國台語夾雜的講法也還沒收錄，這部分需要懂的人來補。

## 六、重要的設計決策與理由

**不評判，只描述。** 禁止「太多」「不足」「應該」「建議」這類字眼。理由是每個人的目標不同，評判可能誤導；而且罪惡感會讓人不想繼續使用。

**正面指示比否定式有效。** 實測發現「不要評論食物營養」模型學不會，改成「聊到吃的，只問怎麼做、好不好吃、跟誰一起吃」就守住了。寫規則時優先想「該做什麼」。

**不說要陪對方去哪裡。** 早期版本模型講出「我可以陪你一起去逛逛」，對獨居長輩來說是做不到的承諾，期待落空的代價很高。這也是排除「孫子」角色的同一個理由。

**數字放畫面，助理不唸數字。** 三句話塞不下運動、飲食、遊戲三件事。步數、餐數用卡片呈現，助理只講一句跟今天有關的話。這也符合 TTS 考量——沒人想聽機器唸一串數據。

**沒運動的日子不要點名。** 「今天只走了八百步」這句話，「只」字就是評判。只在有東西可肯定時才提數字。

**句數限制讓位給安全。** 三句話的規則是為了 TTS 好聽，屬於體驗問題。實測發現模型在紅線題目上常講四句，而第四句「你有跟醫生討論過嗎」正是最重要的一句。兩者衝突時安全優先，所以不做截斷。

**prompt 可從外部覆寫，但要開關控制。** `ALLOW_PROMPT_OVERRIDE` 環境變數，測試時設 true，正式環境不設。沒有這道開關的話，任何拿到密鑰的人都能把阿明換成別的角色，繞過所有安全規則。

**遊戲化要跟語氣原則一起想。** 如果運動功能有連續達成紀錄，斷掉那天使用者會有罪惡感，這跟排除「孫子」角色的理由是同一件事。獎勵機制不要跟助理分開設計。

## 七、目前的技術債

### prompt 存在兩個地方

- `worker/index.ts` 的 `SYSTEM_PROMPT` 常數（正式用）
- `eval/prompt.txt`（測試用）

**內容必須手動同步。** 改一邊忘了改另一邊，測出來的結果就不代表線上行為。

之後應該統一到 Langfuse 的 prompt 管理，或至少寫個同步腳本。

### repo 與開發位置分離

repo 裡的檔案是複製過來的，改動不會互相同步。

長期做法是把開發環境搬進 repo：`wrangler deploy` 直接在 `elder-app/worker` 跑，Promptfoo 在 `elder-app/eval` 跑。需要調整 `wrangler.jsonc` 的路徑設定。

**在搬完之前，團隊協作要約定好誰改哪一份**，否則一定會覆蓋彼此的修改。

## 八、評測

### 現況

15 題 × 3 個模型 = 45 筆。斷言全部是字串比對與程式判斷，不呼叫模型評分，所以跑一次只花 Workers AI 的錢。

**測試類別**：日常閒聊、情緒低落、越界要求、重複提問、拒絕建議、每日回顧、安全紅線。

**目標是 100 到 200 題。**

### 三個模型

| 標籤 | 模型 |
|---|---|
| scout-17b | `@cf/meta/llama-4-scout-17b-16e-instruct` |
| mistral-24b | `@cf/mistralai/mistral-small-3.1-24b-instruct` |
| llama33-70b | `@cf/meta/llama-3.3-70b-instruct-fp8-fast` |

之後若要加 Workers AI 以外的供應商，Promptfoo 原生支援 OpenAI 那些，直接在 `providers` 加，不用經過自家 Worker。

### 一定要加 `--no-cache`

有快取時測出 100%，關掉快取變 96.97%。快取會遮蔽隨機性造成的問題。

### 判斷失敗的原則

**讀了覺得這句話沒問題 → 斷言要改；讀了覺得阿明不該這樣講 → prompt 要改。**

評測集的價值來自它反映團隊的判斷，不是反過來讓團隊遷就它。

實例：早期用 `/[？?]/` 判斷「有沒有在問」，但模型常省略問號，而且輸出會進 TTS，使用者根本聽不到標點。後來改成看疑問詞。

### Git 流程

```powershell
# 開始工作前
git pull

# 做完一段
git add .
git status          # 確認沒有 .env

```

**`git status` 那步不要跳過。** 本專案的開發者曾誤貼密鑰兩次，都已撤銷重建。團隊變大之後這類事故機率只會更高。

`.gitignore` 已涵蓋 `.env`、`node_modules/`、`.promptfoo/`、`.wrangler/`。

### 建議加 CI

每次改 prompt 送 PR 就自動跑 Promptfoo，通過率掉了就擋下來。這是 Promptfoo 最大的價值，比本機手動跑重要得多。

### Cloudflare 權限

目前是個人帳號。團隊協作要加成員並設好權限，**不要共用同一組 API token**，出事查不出是誰。

### 最需要人的三件事

| 工作 | 需要什麼背景 | 說明 |
|---|---|---|
| 寫測試案例 | 不需工程 | 從 15 題擴充到 100 題以上，投報率最高 |
| 補安全關鍵字 | 熟悉長輩實際用語，含台語 | 現有關鍵字表憑常識寫的，一定有漏 |
| 標註規則手冊 | 長照或社工背景 | 什麼樣的回應算好、普通、不能接受 |

**標註規則手冊要先寫。** 兩個人看同一則對話，判斷應該要一致。建議開工前做一次校準：各自標同樣 30 則，比對差異，把不一致的地方寫成規則。沒有這步，標註資料會互相矛盾，微調時就是垃圾進垃圾出。

**特別缺的測試類別**：方言與台語夾雜、家人代操作（「我是他女兒」）、模糊的身體不適（「我這裡怪怪的」）、重複同一個問題、問阿明是不是真人。

## 十一、待辦

### 卡住其他事的

**個人檔案 schema 統一**。飲食 App 用的是出生年、身高、體重、目標、過敏、慢性病；助理這邊規劃的是年齡區間、同住狀況、行動能力、飲食限制、運動頻率、是否服藥中。同一個成品 App 應該只有一份 schema。現在合併只是改欄位，等兩邊都寫完就是資料遷移了。

**服藥閘門**。長輩多在服藥，推薦葡萄柚、納豆、大量深綠色蔬菜可能出事。飲食 App 的週回顧目前完全沒有這道關卡。

**prompt 雙份同步、repo 與開發位置分離**（見第七節）。

### 功能

- 每日摘要的程式實作
- 主題選擇邏輯
- 第二層小模型分類器
- 評測集擴充到 100 題以上
- Langfuse 接入

### 尚未決定

- **健康資料是否出境**。目前傾向：不出境，做法是送給模型的內容去識別化，原始資料留在國內，而非整套搬回地端。這涉及個資法特種個資認定，需要法律專業確認。

## 十二、踩過的坑

### Cloudflare

- **可能把請求路由到別的模型**。log 要分開印「請求的模型」和 `response.model`（實際執行的），兩者不一定一致
- **部署不等於存檔**。改完 `wrangler deploy` 才會生效，網頁編輯器要按 Deploy
- **兩個 Worker 專案的 `src/index.ts` 很容易搞混**，貼錯檔案時第一行的註解是最快的辨識方式

### Windows / CMD

- **CMD 換磁碟機要 `cd /d`**，單獨的 `cd` 不會跨磁碟
- **CMD 讀 UTF-8 檔案會亂碼**，`findstr` 遇到中文會出錯，先跑 `chcp 65001` 或只搜英文字串
- **建 `.env` 容易變成 `.env.txt`**，用 `notepad .env` 建比較保險
- **用 CMD 不要用 PowerShell 跑 curl**，PowerShell 的 `curl` 是別的東西，引號處理會出問題

### 工具

- **YAML 裡 `!` 開頭會被當成型別標籤**，JavaScript 斷言一律用 `>-` 區塊寫法
- **Promptfoo 的快取會遮蔽問題**，一定要 `--no-cache`
- **Git 建 repo 時不要勾初始化選項**，遠端先有 commit 會導致 push 被拒，要 `git pull --allow-unrelated-histories`
- **合併時跳出 vim**：按 `Esc`，輸入 `:wq`，按 Enter

### 模型行為

- **模型會把 prompt 裡的詞當成稱呼**。組訊息時寫「長輩剛剛說」，模型就會用「長輩」稱呼使用者，改成「對方」才解決
- **否定式規則常常無效**。「不要評論營養」講了兩次都沒用，改成正面指示才守住
- **模型會自己腦補沒給的資訊**。摘要沒寫天氣，它會說「今天天氣不錯」

### 資安

- **API 金鑰與密鑰絕對不要貼進聊天視窗**
- **`git status` 每次都要看過再 commit**
